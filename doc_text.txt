RCOD Document – Textile Manufacturing System
Client: Everest Textile Mills  |  Unit of measure: all quantities in kg  |  Stack: MySQL · Python (Flask) or Node.js (Express) · HTML/CSS/JS + React
RCOD is used here as Requirements, Constraints, Objectives, Design. If your institution defines RCOD differently, the content below can be re-sorted under your headings.

1. Introduction
1.1 Purpose
Everest Textile Mills currently runs on notebooks, paper slips, registers and phone calls. This document defines one unified web platform that replaces them: yarn purchase and gate entry, stock monitoring, a FIFO production queue, quality checks, buyer order tracking, dispatch with invoicing, and month-end finances.
1.2 Users (roles)
Role
Who
What they can see/do
Company (admin / staff)
Owner, store keeper, floor supervisor, QC inspector
Everything: yarn, stock, factory status, QC, dispatch, invoices, costs, reports
Customer (buyer)
Fabric buyer
Place orders and check order status only
Supplier
Yarn supplier
See yarn orders raised by the mill (quantity, colour, order number)
1.3 Assumptions
All quantities are in kg (yarn, fabric, rolls).
Yarn is bought already in the required colour, so a fabric order of colour X consumes yarn of colour X.
A fixed wastage factor (default 5%, configurable) is added when calculating the yarn needed for an order: yarn_needed = fabric_kg × 1.05.
Every order passes three stages in this sequence: Spinning → Weaving → Dyeing, each stage done on a machine of that type.
Colours come from a fixed list of 100 Pantone textile colours (Section 4.3).

ID
Requirement
C1
Gate-entry form takes exactly four inputs: quantity received (kg), yarn type, colour, and the company's yarn order number.
C2
System validates the order number exists, is still not_supplied, and that type and colour match that order. Mismatch → clear error, nothing saved.
C3

Module D – Raw Material Stock & Warnings
ID
Requirement
D1
Stock page shows, per (yarn type, colour): available kg, reserved kg, free kg (= available − reserved), and reorder level.
D2
Low-stock warning: if free kg ≤ reorder level, show a red banner/badge on the dashboard and stock page. Each (type, colour) has its own reorder level.
D3
When a new buyer order arrives, the system computes yarn needed and shows "Enough yarn – ready to start" or "Short by X kg – order more".
D4
If short, order status is awaiting_yarn and a button "Create yarn order for shortfall" pre-fills the yarn order form.
D5
If enough, the needed kg is reserved so two orders cannot claim the same yarn. Reservation is converted to consumption as production uses it.
D6
When a yarn order becomes supplied, orders waiting in awaiting_yarn are re-checked automatically (oldest first).
Module E – Production Floor (FIFO Queue & Factory Status)
ID
Requirement
E1
Orders with enough yarn enter a FIFO queue (first in, first out by the time they became ready).
E2
Each queued order is assigned to the first idle machine of the right stage type. When a machine finishes a job and becomes free, the next order in the queue is assigned to it automatically.
E3
Machine states: idle, running, breakdown. A broken machine is skipped by the assigner. If it breaks while running a job, that job returns to the front of its queue.
E4
Company page has a "Factory Status" button opening a page showing for every machine: its state, the order it is on, the stage, progress (kg done / kg target, %), and kg produced today. Idle machines are listed clearly.
E5
Supervisors record production (kg) against a job, with shift and worker. Progress and totals update immediately.
E6
Live total: the company can see at any moment how much fabric has been produced so far today (kg), overall and per machine.
E7
End-of-day report: generated automatically at day end (and on demand): total kg produced today, kg per machine, per order, per shift, with a download (CSV).
Module F – Quality Check (QC)
ID
Requirement
F1

F2

F5

Module J – Machine Management
ID
Requirement
J1
Add a machine: the company page has a Machines page with an "Add Machine" form: machine name, stage type (spinning / weaving / dyeing), capacity (kg per hour, optional) and installation date. A new machine starts as idle, appears on Factory Status at once, and the FIFO assigner runs immediately so a waiting order can be given to it.
J2
See how a machine functions: clicking a machine opens its detail page with current status, current order and stage, progress (kg done / target, %), kg produced today and this month, hours running / idle / broken today, number of breakdowns, defect rate of the rolls it made (from QC), and a dated event history (added, job started, job finished, breakdown, repaired, removed).

4. Objectives
Replace notebooks and calls with one web platform for the whole mill.
Never run out of yarn unexpectedly – stock is always known and low-stock warns early.
Start orders only when yarn is enough, and see shortages instantly.
Keep machines busy – FIFO queue auto-assigns the next order when a machine frees up.
Know the floor at a glance – one Factory Status page and live daily production total.
Trace every defect back to order and machine.
Let buyers self-serve order status, ending status phone calls.
Dispatch correctly – right rolls, right quantity, right buyer, matching invoice, never twice.
Show the true cost of an order and whether the mill made money each month.

5. Design
5.1 Architecture (kept simple)
React UI (Company / Customer / Supplier pages)        |  HTTPS + JSON (REST)   Backend API (Flask or Express)  -- business rules, FIFO, stock checks        |  SQL      MySQL database
Three layers only. All rules (stock check, FIFO assignment, dispatch matching) live in the backend so the UI cannot bypass them.
5.2 Pages
Company page (menu): Dashboard (low-stock alerts, today's kg) · Order Yarn · Gate Entry · Yarn Stock · Buyer Orders · Factory Status (button) · Machines (add / view / remove) · Production Entry · Quality Check · Finished Goods Store · Dispatch & Invoice · Workers & Wages · Month-End Report
Customer page: My Orders (with status) · Place New Order
Supplier page: Yarn Orders received (order_no, colour, type, quantity, status)
5.3 Main workflow
Company orders yarn -> Supplier sees order -> Truck arrives -> Gate entry (4 inputs)   -> status = supplied, stock += kgBuyer places order -> yarn check -> enough? reserve & join FIFO queue : awaiting_yarnQueue -> idle Spinning machine -> Weaving machine -> Dyeing machine (auto next in queue)Dyeing done -> rolls created (order + machine linked) -> QC: pass / rework / rejectPassed rolls -> store (in_stock) -> Dispatch (match buyer+qty) -> InvoicePayments, wages, yarn bills -> Month-end report
5.4 Colour list (Pantone textile)
A colours table stores 100 rows: colour_id, colour_name, pantone_code, hex_value, is_standard. The 12 standard colours (flagged is_standard = 1) are: Red, Orange, Yellow, Green, Blue, Violet, Pink, Brown, Black, White, Grey, Beige. The other 88 popular shades are loaded from a seed CSV (colours_seed.csv).
Please note: I have not hard-coded 100 Pantone codes here because exact TCX codes must match the official Pantone Fashion, Home + Interiors guide. Fill pantone_code and hex_value from that guide (or the list your institution provides) when preparing the seed file.

5.6 Key business rules (how it works)
1. Gate entry (Module C). Input: order_no, yarn_type, colour, quantity.
BEGIN TRANSACTION  order = yarn_orders WHERE order_no = input  if order missing or type/colour differ -> reject with message  insert yarn_receipts row  yarn_stock (type, colour): available_kg += quantity   (create row if new)  if SUM(receipts for order_no) >= order.quantity -> status = 'supplied'  re-check buyer orders in 'awaiting_yarn' (oldest first)COMMIT
2. Low-stock warning (D2). free_kg = available_kg - reserved_kg. Warning when free_kg <= reorder_level.
SELECT t.type_name, c.colour_name, s.available_kg, s.reserved_kg,       (s.available_kg - s.reserved_kg) AS free_kg, s.reorder_levelFROM yarn_stock sJOIN yarn_types t ON t.yarn_type_id = s.yarn_type_idJOIN colours c ON c.colour_id = s.colour_idWHERE (s.available_kg - s.reserved_kg) <= s.reorder_level;
3. New buyer order – enough yarn? (D3–D5).
yarn_needed = quantity_kg x 1.05free = available_kg - reserved_kg  for (type, colour)if free >= yarn_needed:    reserved_kg += yarn_needed ; status = 'in_queue' ; ready_at = NOW()    create spinning job (status 'queued')else:    status = 'awaiting_yarn' ; show 'Short by (yarn_needed - free) kg'
4. FIFO assignment (E1–E3). Run whenever a job is queued, a job completes, or a machine returns from breakdown:
-- for each idle machine of a stage, take the oldest queued job of that stageSELECT job_id FROM production_jobsWHERE stage = :stage AND status = 'queued'ORDER BY queued_at ASC        -- FIFOLIMIT 1 FOR UPDATE;-- then: job.machine_id = machine, job.status = 'running', machine.status = 'running'
When a job's done_kg >= target_kg: job = completed, machine = idle, the order's next stage job is queued (spinning → weaving → dyeing), then the assigner runs again so the freed machine takes the next order. After dyeing completes, rolls are created and the order moves to quality_check.
5. Factory Status page (E4).
SELECT m.machine_name, m.stage, m.status,       j.order_id, j.done_kg, j.target_kg,       ROUND(100 * j.done_kg / j.target_kg, 1) AS progress_pct,       COALESCE((SELECT SUM(kg_produced) FROM production_log p                 WHERE p.machine_id = m.machine_id                   AND DATE(p.logged_at) = CURDATE()), 0) AS kg_todayFROM machines mLEFT JOIN production_jobs j ON j.machine_id = m.machine_id AND j.status = 'running'WHERE m.status <> 'removed';-- machines with status = 'idle' are shown in a separate "Idle machines" section
6. Production till now / end-of-day report (E6–E7).
-- live totalSELECT COALESCE(SUM(kg_produced),0) AS kg_todayFROM production_log WHERE DATE(logged_at) = CURDATE();-- end-of-day breakdown (also saved to daily_reports)SELECT m.machine_name, SUM(p.kg_produced) AS kgFROM production_log p JOIN machines m ON m.machine_id = p.machine_idWHERE DATE(p.logged_at) = CURDATE() GROUP BY m.machine_name;
A scheduled job (cron / node-cron / APScheduler) runs at day end (e.g. 23:59) and stores the result in daily_reports.
7. Quality check (F). Result passed → qc_status='passed', store_status='in_stock', and when every roll of an order is passed the order becomes ready_to_ship. rework → roll goes back to production, then returns to pending. rejected → roll excluded from dispatch. Defect traceability query:
SELECT m.machine_name, q.defect_type, COUNT(*) AS defectsFROM qc_inspections qJOIN fabric_rolls r ON r.roll_id = q.roll_idJOIN machines m ON m.machine_id = r.machine_idWHERE q.result <> 'passed'GROUP BY m.machine_name, q.defect_type;
8. Order status for customers (G). The status is the buyer_orders.status column, updated by the backend at each event (stock check, job start, stage change, QC, dispatch). Mapping shown to customers: placed→Order Placed · awaiting_yarn→Awaiting Material · in_queue→In Queue · spinning/weaving/dyeing→In Production (stage name) · quality_check→Quality Check · ready_to_ship→Ready to Ship · dispatched→Dispatched. Estimated delivery date is shown when the order is in the queue or later.
9. Dispatch with matching invoice (H).
BEGIN TRANSACTION  selected rolls must satisfy ALL of:     roll.order_id = chosen order       (right buyer / right order)     roll.qc_status = 'passed'     roll.store_status = 'in_stock'     (not already sent)  SUM(roll.weight_kg) must equal the order quantity (or is accepted as a     partial dispatch only if the staff confirms)  (right quantity)  insert dispatches, dispatch_items (UNIQUE roll_id blocks double dispatch)  roll.store_status = 'dispatched'  insert invoices: total_kg = SUM(rolls), amount = total_kg x price_per_kg  order.status = 'dispatched' (when all kg are sent)COMMIT
Because the invoice is built from the same list of rolls, it always matches what was loaded.
10. Finished goods on the shelf.
SELECT COALESCE(SUM(weight_kg),0) AS on_shelf_kgFROM fabric_rolls WHERE store_status = 'in_stock';
11. Month-end report (I5). Cost of an order = yarn cost + allocated wages.
Yarn cost = yarn_needed_kg × price_per_kg of the yarn used.
Allocated wages = month's wage total × (order's produced kg ÷ all produced kg that month).
-- kg per machine in a monthSELECT m.machine_name, SUM(p.kg_produced) AS kgFROM production_log p JOIN machines m ON m.machine_id = p.machine_idWHERE DATE_FORMAT(p.logged_at,'%Y-%m') = :month GROUP BY m.machine_name;-- totals for profit/lossSELECT  (SELECT COALESCE(SUM(amount),0) FROM buyer_payments    WHERE DATE_FORMAT(paid_on,'%Y-%m') = :month)     AS money_in,  (SELECT COALESCE(SUM(amount),0) FROM wage_payments    WHERE month_year = :month)                       AS wages_out,  (SELECT COALESCE(SUM(amount),0) FROM supplier_payments    WHERE DATE_FORMAT(paid_on,'%Y-%m') = :month)     AS yarn_out;-- profit = money_in - wages_out - yarn_out
The dashboard shows a clear Profit / Loss figure in green or red.
12. Machine management (Module J).
-- Add a machine (starts idle), log it, then run the FIFO assignerINSERT INTO machines (machine_name, stage, capacity_kg_per_hr, installed_on)VALUES (:name, :stage, :capacity, :installed_on);INSERT INTO machine_events (machine_id, event_type, user_id)VALUES (LAST_INSERT_ID(), 'added', :user);-- Breakdown: machine skipped; its running job returns to the FRONT of the queueUPDATE machines SET status = 'breakdown' WHERE machine_id = :id;UPDATE production_jobs SET machine_id = NULL, status = 'queued'   -- queued_at is keptWHERE machine_id = :id AND status = 'running';INSERT INTO machine_events (machine_id, event_type, user_id) VALUES (:id, 'breakdown', :user);-- Remove (allowed only when broken or idle); soft delete keeps historyUPDATE machinesSET status = 'removed', removed_on = CURDATE(), removal_reason = :reasonWHERE machine_id = :id AND status IN ('breakdown','idle');INSERT INTO machine_events (machine_id, event_type, note, user_id)VALUES (:id, 'removed', :reason, :user);-- Machine detail page: how this machine is functioningSELECT m.machine_name, m.stage, m.status, m.installed_on,  (SELECT COALESCE(SUM(kg_produced),0) FROM production_log    WHERE machine_id = m.machine_id AND DATE(logged_at) = CURDATE()) AS kg_today,  (SELECT COALESCE(SUM(kg_produced),0) FROM production_log    WHERE machine_id = m.machine_id      AND DATE_FORMAT(logged_at,'%Y-%m') = DATE_FORMAT(CURDATE(),'%Y-%m')) AS kg_month,  (SELECT COUNT(*) FROM machine_events    WHERE machine_id = m.machine_id AND event_type = 'breakdown') AS breakdowns,  (SELECT COUNT(*) FROM fabric_rolls    WHERE machine_id = m.machine_id AND qc_status IN ('rework','rejected')) AS defective_rolls,  (SELECT COUNT(*) FROM fabric_rolls WHERE machine_id = m.machine_id) AS total_rollsFROM machines m WHERE m.machine_id = :id;
A "repaired" action sets the machine back to idle, logs the event and runs the assigner again. The FIFO assigner only ever picks machines with status idle, so broken and removed machines are never given work.
